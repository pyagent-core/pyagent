Subject: Recommended architecture for a multi-agent system with tiered trust and controlled data propagation

Thanks for sending this over. I want to push back gently on one framing before giving you the design: "sensitive data must not automatically propagate between agents" is not a feature you bolt onto a multi-agent system after the fact — it has to be the organizing principle of the architecture. Most teams build the agent graph first (who talks to whom, who calls what tool) and then try to retrofit data controls, and that's where these systems leak secrets, PII, and internal documents into places they shouldn't be. So below I'm proposing a design where trust levels and information flow control are first-class citizens, then naming the concrete tools I'd actually use to build each layer.

THE CORE MODEL: TREAT THIS AS INFORMATION FLOW CONTROL, NOT PERMISSIONS

The instinct is to reach for RBAC ("Agent A is allowed to call tool X"). That's necessary but not sufficient, because the dangerous thing in these systems isn't the tool call — it's a piece of data that entered as untrusted (a scraped webpage, a customer email, a document from an external MCP server) ending up, several hops later, concatenated into a prompt that has access to a privileged tool or a different trust domain. Classic role-based access control doesn't track that; information flow control (IFC) does.

Concretely, this means:

1. Every piece of data flowing through the system carries a label (its trust/confidentiality/integrity level), not just every agent.
2. Every agent-to-agent or agent-to-tool edge is checked against those labels before the call is made, not just against which agent is calling.
3. Untrusted content is architecturally prevented from influencing control flow (what tools get called, with what arguments), even if it's allowed to influence data flow.

This is exactly the model Google DeepMind formalized in their CaMeL paper ("Defeating Prompt Injections by Design," arXiv:2503.18813, April 2025) — worth reading regardless of whether you build on it. CaMeL splits execution into a Privileged LLM that plans from the trusted user request only, and a Quarantined LLM that is allowed to read untrusted data but has no tool access, with a deterministic interpreter in between that tracks data provenance and enforces capability-based policy on every tool call before it executes. In their evaluation against the AgentDojo benchmark it eliminated nearly all prompt-injection-driven data exfiltration while preserving task performance — because it doesn't rely on a classifier guessing whether text "looks like an injection," it makes the injected text structurally incapable of reaching a privileged action. This dual-LLM separation (privileged planner / quarantined data-handler) traces back to Simon Willison's original "Dual LLM pattern" write-up, which is a good primer if your team hasn't seen the idea before.

Note there's a naming collision worth flagging so you don't buy the wrong thing: CAMEL-AI (camel-ai.org, github.com/camel-ai/camel) is a popular open-source multi-agent orchestration framework for role-playing agents — completely unrelated to DeepMind's CaMeL security architecture. Don't confuse the two when your team is researching this.

RECOMMENDED LAYERED ARCHITECTURE

Layer 1 — Data classification and tagging. Define your trust levels explicitly up front (e.g., L0 = untrusted external content: web pages, emails, third-party API responses, uploaded documents; L1 = authenticated user input; L2 = internal trusted system data; L3 = secrets/credentials — never enters agent context at all, see Layer 4). Every message, tool result, and retrieved document gets tagged with its level at ingestion and the tag travels with the data through the whole pipeline. This is the taint-tracking backbone everything else hangs off of.

Layer 2 — Orchestration with real state isolation between agents, not just a chat transcript everyone can read. Two credible options depending on how much you want to own:

- Build it yourself on LangGraph. It gives you subgraphs with genuinely separate state, and the handoff pattern (agents returning a Command object to transfer control) lets you strip the supervisor's routing/reasoning out of what the receiving agent sees, so a sub-agent doesn't inherit context it has no business seeing. You get full control over what state crosses each node boundary, which is what you need to enforce Layer 1's tags — but you own the discipline of enforcing it consistently, and LangGraph itself won't stop you from wiring a bad edge.

- Use Anthropic's Managed Agents platform (Claude API) if you want the credential-isolation problem solved for you rather than hand-rolled. Its vault mechanism is a good concrete existence proof of what "sensitive data must not automatically propagate" should look like in practice: a credential lives in a vault, the agent's sandbox only ever sees an opaque placeholder string, and the real secret is substituted into the outbound request at egress — the value is never present in the agent's context window, never loggable via a tool call, and unreachable even under prompt injection, because there's nothing there to exfiltrate. It also gives you per-agent sandboxed containers, MCP credential brokering scoped by server URL, and a coordinator/subagent model with per-thread event isolation. If Claude fits your model requirements, this is the fastest path to "credentials genuinely cannot leak," and it's worth using even just as the design target if you're building something bespoke on another stack.

Whichever you choose, the rule is: no agent's context window should contain a secret, ever — not "the agent is instructed not to repeat it." Instructions are not a security boundary; prompt injection routinely defeats them.

Layer 3 — Policy enforcement on every tool call, independent of the model's judgment. This is where you enforce least privilege per agent and per data-trust-level, and it needs to sit outside the LLM, as a deterministic gate the model cannot talk its way around. Progent (arXiv:2504.11703, "Progent: Programmable Privilege Control for LLM Agents") is the most directly applicable published system here — it's a DSL for expressing allow/deny/fallback rules on tool calls, evaluated at execution time, decoupled from agent internals, and it held up well against AgentDojo, the Agent Security Bench, and AgentPoison in the paper's evaluation. Even if you don't adopt Progent verbatim, replicate its shape: policy-as-code, evaluated outside the model, with explicit rules like "agent X may call tool Y only if all inputs are tagged ≤ L1" or "output of a tool call tagged L0 may never be passed as an argument to a tool tagged L3-capable." This is also exactly what OWASP's 2026 Top 10 for Agentic Applications is pointing at with its "least agency" principle (ASI03, Identity & Privilege Abuse; ASI07, Insecure Inter-Agent Communication) — worth pulling their full list as your acceptance-criteria checklist, since it also covers goal hijacking and tool misuse, which are the failure modes adjacent to what you're asking about.

Layer 4 — Secrets and credentials never enter the LLM context at all, full stop. Use a vault pattern with egress-time substitution (Anthropic Managed Agents vaults, or roll your own broker in front of HashiCorp Vault / AWS Secrets Manager that swaps a placeholder for the real value only on the outbound HTTP call). If an agent needs to call a third-party API, the API key should be injected by your infrastructure at the network edge, not handed to the agent as a string it could echo, log, or leak into another agent's context.

Layer 5 — Execution sandboxing per trust domain. If any agent executes code or browses the open web (both are your highest-risk L0 ingestion points), run it in a hardware-isolated sandbox — Firecracker microVMs or gVisor/Kata Containers, not a shared container namespace — and give it no network path to your internal services. Microsoft's own AutoGen ecosystem has had real incidents here worth learning from rather than repeating: AutoGen Studio's local control channel accepted any "localhost" origin, and a browsing agent's headless browser counted as localhost, which turned a bystander agent into a privilege-escalation path into a control plane that assumed it was talking to a trusted operator. The lesson generalizes: any agent that can fetch untrusted content and any agent that has a privileged control channel must not share a network namespace.

Layer 6 — Inter-agent transport and third-party tools. If you're integrating external tools via Model Context Protocol, treat every MCP server as its own trust boundary and assume tool descriptions themselves are attacker-controlled text ("tool poisoning" — hidden instructions embedded in a tool's metadata that the model reads and follows even though the user never saw them). Pin server allowlists, diff tool schemas on every connection rather than trusting them blindly, and never let an MCP-sourced tool description or result cross into your Layer 3 policy engine as if it were operator input.

CONCRETE STACK I'D RECOMMEND FOR A GREENFIELD BUILD

- Orchestration: LangGraph if you need full custom control and are willing to own the isolation discipline; Anthropic Managed Agents (or the Claude Agent SDK if you want to self-host the loop) if you want vault-based credential isolation and sandboxing largely handled for you.
- Injection/data-flow defense: implement the CaMeL privileged/quarantined split for any agent that both reads untrusted content and has tool access — this is the highest-leverage single design decision you can make.
- Tool authorization: a Progent-style policy DSL, or a hand-rolled equivalent, sitting between every agent and every tool call.
- Guardrails for content-level checks (PII detection, output filtering) between agent boundaries: NVIDIA NeMo Guardrails or Guardrails AI, as a belt-and-suspenders layer — not a substitute for Layers 1-4, since content filters are heuristic and get bypassed; they're a second line of defense.
- Secrets: vault + egress substitution, never in-context.
- Sandboxing: Firecracker/gVisor for anything executing code or fetching arbitrary URLs.

VALIDATION

Before you ship, red-team the system against AgentDojo (the standard benchmark both CaMeL and Progent were evaluated on — it specifically measures prompt-injection-driven data exfiltration and unauthorized tool use across realistic agent tasks), and run the OWASP Top 10 for Agentic Applications 2026 checklist against your design, particularly ASI01 (Agent Goal Hijack), ASI02 (Tool Misuse), ASI03 (Identity & Privilege Abuse), and ASI07 (Insecure Inter-Agent Communication). If you can't point to a specific architectural control for each of those four, the design isn't done yet.

Happy to go a level deeper on any one layer — the policy DSL design and the CaMeL-style planner split are the two places teams most often ask for a worked example.
